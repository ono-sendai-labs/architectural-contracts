# Review Notes

## Consistency check

Cross-checked across all documents; no contradictions found in these areas:

- CLI flags, error strings and exit codes agree between `interfaces.md` and `workflows.md`.
- The eight/six self-check component split and its cgo cause are stated consistently in
  `codebase_info.md`, `architecture.md`, `workflows.md`, and `dependencies.md`, and match the
  justfile comment and README limitation 15.
- The 13 capability names appear once (`data_models.md`) with the sync invariant recorded once
  (`dependencies.md` §6).
- Package dependency edges in `architecture.md`, `components.md`, and `dependencies.md` agree.
- The finding-kind table (`data_models.md`) covers exactly the ten `report.Kind` constants.

## Known gaps in this documentation set

1. **`manifest/gen/component.pb.go` was not analyzed.** Generated code, deliberately skipped.
   It is regenerated by `just gen` and guarded by `gen-is-clean`; treat `component.proto` as
   the source of truth.
2. **`checker.Check`'s internals are described by rule, not by implementation.** The exact
   algorithm for each of FR3/FR4/FR5/FR6/M7 — in particular how prune keys are matched against
   normalized symbols — is summarized rather than traced. Read `checker.go` before modifying a
   rule.
3. **`goanalysis`' generic-symbol canonicalization is under-documented.** The hand-rolled
   recursive-descent `symbolTypeParser` and the A4 rewriting rules are named but not specified.
   This is the subtlest code in the repo and would repay a dedicated design note.
4. **The design documents under `.agents/planning/` were not folded in.** Seven planning
   directories exist, including a recent `2026-08-04-compositional-component-analysis` note
   and an implementation review. Requirement codes (FR*, M*, A4, C9–C12) are cited throughout
   the code but their authoritative definitions live there, not here. A reader chasing a
   requirement number should go to `.agents/planning/`.
5. **`bazel_rules/go/tests/testdata/` fixtures are listed by name, not by scenario.** Twenty-odd
   fixture packages exist; which failure each one is designed to trigger is recorded only in
   the `BUILD.bazel` target names.
6. **No performance characteristics are documented.** SSA + VTA construction cost on large
   closures, and how it scales with member count, is unmeasured here.
7. **`docs/rationale-and-concepts.md` pillar 4 (data-flow / privacy contracts) is summarized
   but unimplemented.** Nothing in the code corresponds to it. Do not treat it as describing
   current behavior.
8. **Version drift risk noted, not solved.** `MODULE.bazel`'s Go SDK `1.26.4` and `go.mod`'s
   `go 1.26` are kept aligned by a comment only — no test enforces it.

## Recommendations

- **Highest value next**: a short design note on symbol canonicalization and prune-key
  matching (gap 3). It is the area where a wrong change would fail silently rather than loudly.
- Consider a tiny test asserting the `MODULE.bazel` SDK version matches `go.mod` (gap 8) —
  every other cross-artifact invariant in this repo already has one, which makes this the odd
  one out.
- Consider a `README` or index under `.agents/planning/` mapping requirement codes
  (FR1, FR2, …, M9, A4, C9–C12) to the documents that define them. The codes are cited in
  dozens of places in code and tests; there is currently no lookup table.
- `bazel_rules/go/tests/testdata/*/BUILD.bazel` would benefit from one-line comments naming the
  scenario each fixture exercises (gap 5).
- Re-run this summary in update mode after any change to `component.proto`,
  `bazel_rules/go/private/`, or the core/shell package boundaries — those are the three places
  where these documents would go stale fastest.

## Maintenance

Update with:

```
/codebase-summary        # detects .agents/summary/last_commit and runs in update mode
```

`last_commit` holds the baseline revision. Update mode diffs commits since that revision and
refreshes only the affected sections.
