# Rough Idea: arcc as a Bazel Rule

I want to make arcc work as a Bazel rule. Approx what I imagine this would look like:

`BUILD` file:

```python
load("@rules_go//go:def.bzl", "go_library")
load("@rules_arcc//go:def.bzl", "go_architectural_component")


go_library(
    name = "service_api",
    srcs = ["service_api.go", "api_types.go"],
    deps = [ ":service_internal" ],
    visibility = ["//visibility:public"],
)

go_library(
    name = "service_internal",
    srcs = [ "impl1.go", "impl2.go"],
    deps = [
        ":more_internal_deps",
        "//path/to/other/pkg",
    ],
    visibility = ["//visibility:private"],
)

go_architectural_component(
    name = "service_api_component",
    interface = [
        ":service_api",
    ],
    contract = [ "component-contract.md", "docs/contract-details.md" ],

    component_deps = [
        "//path/to/other/pkg:component", # must be go_architectural_component target
        ...,
    ],
    declared_authority = ["//.../authority:FILES"],  # could also just use strings, but using labels provides type checking.
    visibility = ["//visibility:public"],
)
```

The `go_architectural_component` target expands into two targets:

a. a target that generates the component manifest.
   - Its `interface_files` are the srcs of the targets listed in `interface`
   - Its `component_dependencies` are the manifests generated by the component_deps targets
   - All other deps become absorbed_dependencies

b. A test target that executes `arcc check` on the generated manifest

## Thoughts / Questions

### 1. Explicit implementation files

We'll probably have to extend arcc and the manifest so it allows specification of implementation files after all (we'd initially settled on "all packages under the directory the manifest is in are part of the component"); but with Bazel everything is specified explicitly, so we should reflect that.

- We may also want to lift the requirement that the manifest is colocated with the component's sources; this would allow creating manifests without having to modify upstream sources.

### 2. Rule shape: reference existing go_library vs. generate it

The above sketch has the `go_architectural_component` rule depend on the library rule to provide the interface and all transitive deps. This is nice because the component target can more easily be added to existing BUILD files. The alternative is to have the `go_architectural_component` specify everything, and have it generate the go_library target containing the public API sources.

Something like:

```python
go_architectural_component(
    name = "service_api_component",
    interface_srcs = ["service_api.go", "api_types.go"],
    contract = [ "component-contract.md", "docs/contract-details.md" ],

    component_deps = [
        "//path/to/other/pkg:component", # must be go_architectural_component target
        ...,
    ],
    declared_authority = ["//.../authority:FILES"],
    visibility = ["//visibility:public"],

    internal_srcs = [ "impl1.go", "impl2.go"],
    deps = [ ... ] # internal and external absorbed deps.
)
```

Tradeoff considerations:

- One benefit of the latter approach is that we don't need to duplicate the other/pkg:component dependency, it could be automatically generated.
- A benefit of the first approach is that it requires the interface to be defined as a separate go_library rule with explicit dependencies on the internals; if the go_architectural_component rule generates everything it could be difficult to debug if there are missing deps (but maybe that's not an issue?)
- In the latter approach the library rule that e.g. a test would depend on might have to be specified explicitly as the one with the generated name, like:

```python
go_test(
    name = "service_test",
    srcs = [...],
    deps = ["service_api_component_library"] # target generated by the go_architectural_component target
)
```

Or would it be possible to make it work so that tests (and other, not-yet-component-ized dependents) can depend directly on `...:service_api_component` in their `deps`, and it'll "just work"?

- Any additional tradeoffs you can think of?
