# Layout completeness on rewriting hosts, and a vendored-stdlib import fix

**Date:** 2026-07-24
**Branch:** `dev/exp-go-bazel-mvp`

> After-the-fact record of making `go_component` `.check` targets work for real
> consumers inside a large Bazel monorepo whose Go rules differ from rules_go. It
> documents two things arcc's layout-backed analysis needed that the MVP had not
> exercised: a **complete** package graph on a host whose build providers
> under-report, and correct **vendored standard-library** import resolution. It
> also records a design (export-data-backed analysis) that was investigated and
> shelved, and why.

## Context

arcc's hermetic analysis (see `2026-07-16-bazel-arcc-rules`) loads a
`package-layout.json` naming every package in a component's closure — its sources
and import edges — and type-checks + capability-analyzes it through a self-exec
`GOPACKAGESDRIVER`. The layout is normally produced in Starlark by an aspect that
walks the interface library's `deps`/`embed` graph (the `go_adapter` seam, see
`2026-07-23-host-portability-seams`). That is sufficient under rules_go. Porting
to a host with its own Go rules exposed two gaps.

## Problem 1 — the aspect cannot always see a complete package graph

Some Go build systems pull a package's real dependencies in through channels an
aspect cannot traverse. The concrete case was generated protobuf code: the
generated `.pb.go` imports a proto runtime that the build injects through the
**toolchain**, not through the target's `deps`. So an aspect walking `deps`/`embed`
never creates layout nodes for those runtime packages, and the layout is
incomplete. arcc then fails the check — correctly: `LoadPackageFacts` collects
load/type errors across the whole graph and fails on any missing dependency. (An
earlier host-local edit had scoped error collection to root packages only; that
was a fail-open workaround and was removed.)

Two properties made this unfixable at the aspect layer on that host:

- The per-target import lists the providers expose **under-report** generated
  code — a generated package's provider listed only one of the runtime imports its
  source actually uses. So the *edges* were not available there either.
- No provider mapped import path → export file for the unreachable runtime
  packages, so they could not even be synthesized as nodes.

**The complete graph did exist** in the host build's package metadata (the data
its own `gopackagesdriver` consumes): one metadata record per transitively
*linked* package — aggregated through the actual compilation, hence including the
toolchain-injected runtime.

### Resolution — generate the layout from the host's package metadata (a seam)

On such a host, the layout is generated by a small build tool that reads the
complete package-metadata set for a component's closure and emits
`package-layout.json`, recovering each package's real import edges by parsing its
(build-constraint-filtered) sources and keeping only edges that resolve to a known
node or to the standard library (so build-tag-gated imports that were never linked
are dropped). arcc's loader is unchanged.

This is a **host seam**, not a change to arcc's model: under rules_go the aspect's
`deps` graph is already complete (its `go_proto_library` exposes the runtime as
ordinary dependencies), so rules_go keeps the Starlark layout. The lesson for arcc
is that layout *generation* is a legitimate seam — a host may need to source the
graph from its build metadata rather than from a `deps` walk — while the layout
*schema* and loader stay host-agnostic.

## Problem 2 — vendored standard-library imports did not resolve

Independently, checks whose closure reached the standard library's `net` failed on
`golang.org/x/net/dns/dnsmessage` ("no metadata"). `net` imports that package by
its **bare** path; the SDK satisfies it from `GOROOT/src/vendor/...`.

**Root cause (reproduced in isolation —
`TestDiscoverStdlib_VendoredImportKeyedByBarePath`):** `discoverStdlib` keyed the
resolved import under the **`vendor/`** path, but go/types resolves an import by
the path as written in source (the bare path). The bare lookup missed, leaving an
unresolved package; and because go/packages propagates `needsrc` *upward*, that
single miss cascaded ("sources missing") to every importer.

**Fix (host-agnostic — a real bug in the layout loader):** key the discovered
stdlib package's `Imports` by the **bare source path**, with the vendored package
as the target ID; and relax the layout validator's PkgPath check to accept a
`vendor/`-prefixed target for a bare import key. See
`internal/packagelayout/packagelayout.go` (`discoverStdlib` and
`ValidateAndResolve` phase 3) and the two tests in `packagelayout_test.go`.

## Investigated and shelved — export-data-backed analysis

The appealing optimization was to analyze only a component's *own* packages
(members + non-generated absorbed) from source and load everything else — covered
dependencies and generated code — from compiled **export data**. This matches the
component model (covered dependencies are certified by their own components) and
shrinks layouts. It does not work without one prerequisite the host did not
provide, and the reason is worth recording:

- go/packages loads a package from export data only when `NeedDeps` is absent and
  the package has valid export data; and it propagates `needsrc` **upward** from
  any source-only package to all of its importers.
- The standard library is served **from source** (no compiled stdlib export data
  was available). Every stdlib leaf is therefore source-only, and the upward
  cascade forces *every* importer — including the export-data packages — back to
  source, which they do not have.
- Reading export data also requires the full transitive package set present as
  nodes with edges (go/packages builds a `view` — the transitive closure of a
  package's imports — before reading export data; a missing node panics). Export
  data removes the need for dependency *source*, not for a complete graph.

Export-data-backed analysis therefore needs compiled standard-library export data
(and ideally per-package export data for the whole closure). Until that exists, the
host uses **all-source** analysis over the now-complete layout: correct and
fail-closed (it analyzes more, never less), at the cost of type-checking the
closure.

## Outcome

With a complete layout and the vendored-stdlib fix, the real component checks run a
complete, correct analysis (no tool errors). Leaf components conform; components
that transitively reach ambient authority (e.g. through a logging library) report
`UNDECLARED_AUTHORITY` — a real, fail-closed finding rather than a fail-open pass.
The component whose absorbed closure includes generated proto code — which first
surfaced Problem 1 — type-checks against the complete layout. arcc's own test
suite stays green.
